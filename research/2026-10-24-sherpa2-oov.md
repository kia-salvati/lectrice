## Method

- **Source checked, not guessed.** The files at tag `v2.0.0` of k2-fsa/sherpa-onnx: `offline-tts-kokoro-impl.h`
  (`Generate`, `TokenizeFromLexiconStr`, `ReplacePunctuations`, `IsPunctuation`), `text-utils.cc` (`NormalizeLexiconKey`,
  `ParseLexiconFile`, `SplitStringAndTrim`, `SplitByAllPunctuation`, `IsCJK`) and `offline-tts.cc` (it passes the text
  straight to the impl). The crate doesn't vendor the C++ source, so the files came from the GitHub tag.
- **What 2.0 does, in order:** no text-normaliser FSTs (our adapter sets none). `:` becomes `,`. NFC. Then it
  splits words **only** at ASCII space/tab/CR/LF and `, . ! ? ; :`. Everything else stays part of the word: quotes,
  brackets, slashes, curly apostrophes, dashes, `%`, `&`, non-breaking spaces. It looks each word up as NFC→lowercase→NFC
  in `lexicon-us-en.txt` (the only lexicon our adapter loads). If the word isn't there and contains `-`, it looks up
  each part. Otherwise it skips the word and logs `OOV word skipped`. Splitting into sentences and merging chunks never
  joins two words, and US-English keys are single tokens, so the longest-match loop never matches more than one word.
- **Two lexicon facts that explain most of the numbers:** `lexicon-us-en.txt` has **no digits at all** (every number
  is skipped), and it lacks many **regular inflected forms** of common words (-s, -ed, -ing). misaki, which the lexicon
  comes from, builds those forms with rules that sherpa doesn't have.
- **Text measured:** the core's real pipeline (pdfium → `RuleBasedCleaner`, cleaner v3 → sentencex), then every
  sentence in `playback_order` with "read code & tables aloud" off (so code and tables count as their spoken cues), as
  `spoken_text()`, with NUL removed like the adapter does.
- **Counting:** a *word* is a 2.0 token with at least one letter or digit. A word counts as *skipped* if any of its
  parts is dropped. Symbol-only tokens (a lone dash or `&`) are counted separately: 48–426 per book, silent on both
  versions. The denominator is always the original words, so spelling `AWS` as three letters doesn't inflate it.
  Categories overlap: all-caps (≥ 2 letters, all upper), contains a digit, camelCase (lower then upper), attached
  punctuation (any character other than a letter, digit, ASCII `'` or `-`), other (none of these).
- **Counter checked against the real engine:** on an invented test sentence (acronyms, numbers, quotes, curly
  apostrophes, a dash, `%`, `&`, hyphenated words), the counter predicted 19 skipped units and sherpa 2.0 printed exactly
  19 `OOV word skipped` lines. Only the count of those lines was kept; the logs were never saved.
- **Prototype fixes** (test code only; each fix touches only a word 2.0 would skip, and a word the lexicon knows is
  left alone):
  1. **§14.2 as written:** split camelCase (`getUserId` → get User Id, `HTTPServer` → HTTP Server), split letter/digit
     mixes (`k8s` → k 8 s), and spell all-caps words that aren't in the lexicon letter by letter.
  2. **+ numbers:** digit runs become words (cardinals up to 12 digits, else digit by digit; `1st`/`21st` become
     ordinals). This is needed because the lexicon has no digits.
  3. **+ punctuation:** curly apostrophes become `'`. Inside a skipped word, `& % + @` become words and other symbols
     become spaces.
  4. **+ suffix rules:** a word also counts as known if it is a known stem + `-s/-es/-ies/-ed/-ied/-ing/'s`
     (with e-drop and doubled consonants). In the real engine this needs phonemes, not text (see "To ship").

Tool: `lectrice-sherpa2/backend/crates/lectrice-api/examples/oov_check.rs` in the sherpa2 worktree (not committed),
`cargo run -p lectrice-api --example oov_check -- books <lexicon> <libpdfium.so> ~/Desktop/*.pdf`.

## Accelerator desk check (M-o, spec §15.5)

ORT 1.31.0 `python -m onnxruntime.tools.check_onnx_model_mobile_usability` (venv `~/.local/opt/ort-venv`):

| Model | NNAPI as is | NNAPI if shapes were fixed | ORT's verdict |
|---|---|---|---|
| fp32 `model.onnx` | 1,094 / 2,359 nodes (46.4 %) in **64 partitions** | 2,061 / 2,359 (87.4 %) in 106 partitions | "not recommended … worse performance than just using the CPU EP"; "For optimal performance the model should be used with the CPU EP" |
| int8 `model.int8.onnx` | 1,547 / 3,134 nodes (49.4 %) in **98 partitions** | 2,565 / 3,134 (81.8 %) in 139 partitions | same |

- 1,115 (fp32) and 1,222 (int8) nodes are rejected only because their input shapes are dynamic. The others fail on
  operators NNAPI doesn't support: `LSTM`, `InstanceNormalization`, `ConvTranspose`, `Loop`, `If`, sequence ops,
  `CumSum`, `Range`, `Cos`, `Atan`, random ops, and for int8 also `ConvInteger`, `MatMulInteger`, `DynamicQuantizeLinear`.
  Fixing the shapes still leaves over 100 partitions, so the answer stays no.
- The checker doesn't cover **XNNPACK**, so I estimated it by hand. The EP's kernel list (ORT v1.31.0
  `xnnpack_execution_provider.cc`) has `Conv`, `ConvTranspose`, `Gemm`, `MatMul`, `Softmax`, `Resize`, pools and
  `QLinear*`, with the support rules from its `IsOnnxNodeSupported` checks (Conv needs a fixed channel count and length
  plus constant weights; MatMul/Gemm need a constant 2-D B). Applied to ONNX shape inference of the graph:
  - fp32: about **95 of 3,396 compute nodes (≈ 3 %)**: the 73 small `Gemm` (style projections), 12 `Softmax` and 10
    `MatMul`. **None of the 97 Conv/ConvTranspose** (most of the compute), because the time length is dynamic.
  - int8: about **12 nodes** (the `Softmax`). Its quantized convs and matmuls are `ConvInteger`/`MatMulInteger`
    (dynamic quantization), which XNNPACK has no kernels for.
- **Expectation:** `nnapi` won't help and may be slower; `xnnpack` will be about the same as `cpu` or slightly worse
  (copies between partitions). This matches spec §15. The phone runs (M-m) are still the real test, but neither
  provider is likely to pass the "≥ 15 % faster" bar.

## What shipping the fixes would take (if 2.0 is revisited)

1. **Where the code goes:** the fixes depend on the lexicon (a known word must be left alone), and only the Kokoro
   adapter (`lectrice-infra/src/speech/kokoro.rs`) may know about the lexicon. So the fixes go in the adapter as a
   front end, not in the domain. The engine-neutral parts (straight apostrophes, symbols to words, numbers to words)
   could be a small pure normaliser that every engine uses. But 1.13.8 already reads numbers through espeak, so only
   2.0 gains from them.
2. **Suffix rules need phonemes.** Text can't say "makes" if the lexicon lacks it. There are two ways:
   - **(a)** Generate an extra lexicon file offline (known stem + -s/-ed/-ing with misaki's phoneme rules) and pass it
     after the main one. sherpa takes a comma-separated `lexicon` list. Also add a small list of tech words.
   - **(b)** Write our own front end and pass phonemes. The 2.0 Rust `GenerationConfig` has `phoneme_codepoints` and
     `tokens`, verified in `sherpa-onnx-2.0.0/src/tts.rs`.
3. **Even then, 2.5 % / 4.9 % is left.** It is names, tool names and words the dictionary lacks. Only a
   grapheme-to-phoneme fallback for unknown words closes that gap: a permissive model or a rule engine, fed through
   (b). That is a research item (spec §14.2 "later"), not a simple fix.
4. **Logs:** 2.0 prints each skipped word to stderr (logcat on Android), and the Rust API has no switch to turn that
   off. With (b) nothing is ever skipped, so nothing is logged; otherwise the lines must be filtered.
5. **Cache:** any change to the front end changes the audio, so it needs a new engine id (or a front-end version in
   the cache key).
