# Lectrice: research findings (2026-10-05)

Goal: a free, local app like Speechify. You give it a PDF, it cleans up the text and reads it aloud
in a realistic woman's voice. Anyone can download and use the voice.

## Machine reality check

| Machine | GPU | Free disk | Role |
|---|---|---|---|
| Desktop (this one) | RTX 3080, 10 GB | 11 GB | Write code and plan; no model downloads |
| **Laptop** | **RTX 3080 Ti Laptop, 16 GB** | **~100 GB** | Download models, run the listening test and the app |

### Takeaways
- **"Usable by anyone" decides the license.** Breeze, Fish, Voxtral and Higgs sound best, but their
  weights are non-commercial. That's fine for personal use, but it limits sharing and any paid use.
  Kokoro, Chatterbox and Qwen3-TTS are fully permissive.
- **We don't need to train a voice model.** Fine-tuning takes hours of clean recordings of one
  speaker. In 2026 the practical route is:
  1. **Design** the voice: Qwen3-TTS VoiceDesign with a prompt like *"warm, calm woman in her 30s,
     clear American accent, audiobook narrator, gentle pace"*.
  2. Save a 10 to 20 s clip of that voice as a **reference file** (`voices/<name>.wav`).
  3. **Clone** from that clip for every chunk (Qwen3-TTS Base or Chatterbox), so the voice stays
     consistent across the whole book.
  That reference wav is the voice anyone can download. It's original, so nobody's likeness is involved.
- **Kokoro is the fast fallback.** It's near real-time even on CPU and works on laptops without a
  GPU, with slightly less natural prosody.

## 2. PDF cleanup ("Speechify-style skipping")

What we want to skip: running headers/footers, page numbers, footnotes, citation markers `[12]`,
reference lists, figure/table captions, URLs, hyphenation across line breaks, and multi-column order.

| Tool | Type | Strengths | Cost |
|---|---|---|---|
| PyMuPDF / pymupdf4llm | Rule-based, no ML | Very fast. Gives font size/position per block, so we can drop repeated top/bottom lines and small-font footnotes | Tiny |
| Docling (IBM, MIT) | Layout ML | Labels blocks as page-header, footnote, caption, etc., which maps directly to "skip". Has OCR | ~1-2 GB models, CPU OK |
| Marker | Layout ML | Best born-digital accuracy (olmOCR-Bench 76 vs Docling 64) | GPU, heavier, GPL code |
| PP-DocLayoutV3 (ONNX) | Layout model | What OpenReader uses | Small |

Suggested approach: **Docling labels plus our own rules.** Keep body text and headings. Drop
headers, footers, footnotes, captions and the references section. Then run regex cleanup for
citations, URLs and de-hyphenation, and split into sentences for TTS and highlighting.

## 3. Existing open-source apps (reuse or learn from)

- **OpenReader** (MIT): Next.js reader with PDF/EPUB, word-level highlighting (Whisper alignment),
  layout-aware PDF parsing, MP3/M4B export. Supports Kokoro/Orpheus servers. Heavy stack
  (NATS, SeaweedFS). https://github.com/richardr1126/openreader
- **OpenWebTTS**: "open source Speechify alternative", local, any TTS engine.
  https://github.com/Gyyyn/OpenWebTTS
- **sgj0/tts**: same pitch, smaller. https://github.com/sgj0/tts

Option to consider: plug our own voice server (OpenAI-compatible `/v1/audio/speech`) into
OpenReader instead of writing a reader UI from scratch.
