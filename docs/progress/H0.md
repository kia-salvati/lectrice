# H0: spikes for "Desktop helps the phone" (laptop part)

Date 2026-11-13. Machine: AMD Ryzen 9 6900HX (16 logical CPUs), 13 GB RAM, on AC power, Fedora 44, other agents running
(background load ≈ 2). Throwaway bench crate outside the repos (scratchpad `h0-bench`), linking the core by path
(`lectrice-infra` features `kokoro` + `sherpa-static`, sherpa-onnx 1.13.8 static), `KokoroSpeechEngine::load` with the
desktop's thread rule: 16 / 2 = **8 threads**, provider `cpu`, voice `af_heart`. Invented sentences only (generated
from word lists; no book text).

Items that need a phone or Windows are at the end (moved to H5).

## 1. Desktop RTF (synthesis time ÷ audio time)

~188 s of audio per bundle (sentences of ~15 words), engine warm.

| Bundle | Model file | RTF | Speed | 30 listening-min fill at 1× |
|---|---|---|---|---|
| Full (`kokoro-multi-lang-v1_0`, fp32) | `model.onnx` | **0.254** | 3.9× real time | ~7.6 min |
| Fast (`kokoro-lectrice-q8-…`) | `model.int8.onnx` | **0.186** | 5.4× | ~5.6 min (measured: 30 min of audio in 341 s) |
| Small (`kokoro-lectrice-w8-…`) | `model.int8.onnx` | **0.227** | 4.4× | ~6.8 min |

The file-24 figure "≈ 4.4× real time" (fp32, 2026-10-21) is now 3.9× for Full under today's background load; Fast is
the quickest on the desktop too.

## 2. First-sentence latency (11-word sentence ≈ 4.3 s of audio)

Cold = first `synthesize` right after `load` (10 load cycles in one process; the model file was in the page cache, so a
first-ever start after boot will be slower by the disk read). Warm = 40 runs after one warm-up.

| Bundle | Load | Cold p50 / p95 | Warm p50 / p95 / max |
|---|---|---|---|
| Full | 0.86 s | 0.92 / 0.97 s | 0.94 / 1.09 / 1.14 s |
| Fast | 0.71 s | 0.79 / 0.86 s | 0.78 / 0.89 / 0.93 s |
| Small | 0.69 s | 0.95 / 1.00 s | 0.97 / 1.09 / 1.13 s |

- No real "cold penalty": the first synthesis after load costs the same as later ones.
- Spec target p95 < 1.2 s for a 10-word sentence: **met by all three bundles** (worst p95 1.09 s).
- **Decision: keep `HELPER_NOW_GRACE_MS = 1500`.** Worst p95 1.09 s + FLAC encode/decode (< 2 ms for 5 s of audio, §3)
  + one LAN round trip (~10–50 ms) leaves ~0.3 s margin. Lowering it below ~1300 would drop desktop clips that are about
  to arrive; raising it gains little because the local fallback races anyway (first writer wins).
- Not covered by the grace: (a) the desktop already busy with an item (one synthesis at a time; a 25-word sentence takes
  ~2.3 s on Full); (b) a helper engine that is not loaded yet (+0.7–0.9 s load). (b) is handled by loading on `Open`
  (before the first `urgent`); (a) is what the local race is for. For comparison the phones need ~1.6 s (S26, Fast RTF
  0.38) and ~4.8 s (S10+, Fast 1.11) for the same sentence, so waiting for the desktop is the better bet.

## 3. FLAC over 30 min of speech (Fast, 195 clips, 16-bit 24 kHz mono)

`flacenc` 0.5.1 (Apache-2.0) to encode, `claxon` 0.4.3 (Apache-2.0) to decode. Encoded **per clip** (what the wire
sends) and as one continuous stream for comparison. Times are per minute of audio on this laptop.

| Config | Size | % of PCM | kbit/s | Encode | Decode (claxon) | Round trip |
|---|---|---|---|---|---|---|
| PCM WAV | 86.5 MB | 100 % | 384 | | | |
| **flacenc default, 1 thread** (block 4096, LPC order 10, precision 15, Tukey 0.4) | **47.2 MB** | **54.5 %** | **209.4** | **65 ms** (~920× real time) | **17 ms** | bit-exact, 195/195 |
| LPC order 8 (closest to `flac -5`), 1 thread | 47.3 MB | 54.6 % | 209.8 | 56 ms | 17 ms | bit-exact |
| default, multithread (16 workers) | 47.2 MB | 54.5 % | 209.4 | 15 ms | 18 ms | bit-exact |
| default, one 30-min stream | | 54.6 % | 209.5 | 82 ms | 17 ms | bit-exact |

- Confirms file 24 §3.8 (≈ 207 kbit/s, 54 %). While filling: 209 kbit/s × 5.4 (Fast) ≈ **1.1 Mbit/s**, Full ≈ 0.8 Mbit/s.
- **Decision:** use flacenc's defaults with `multithread = false` (encoding is < 0.2 % of synthesis time; no need for
  extra threads next to the engine). "Level 5" is not a flacenc concept; LPC order 8 vs 10 makes no difference here.
- **Bug found (must handle in C41):** flacenc writes the size of the short **last** block into STREAMINFO
  `min_block_size`. The FLAC spec excludes the last block; claxon rejects any stream with `min_block_size < 16`
  (`FormatError("invalid block size, must be at least 16")`). It hits any clip whose length mod 4096 is 1–15 samples
  (≈ 1 clip in 270; the first 30-min run crashed on one). Reproduced with synthetic clips of 4101, 8193 and 4111
  samples; 4112 is fine. Fix (verified bit-exact on all of them):

```rust
use flacenc::{component::BitRepr, error::Verify};
let cfg = { let mut c = flacenc::config::Encoder::default(); c.multithread = false; c.into_verified().unwrap() };
let src = flacenc::source::MemSource::from_samples(&samples_i32, 1, 16, 24_000);
let mut stream = flacenc::encode_with_fixed_block_size(&cfg, src, cfg.block_size)?;
let max = stream.stream_info().max_block_size();
stream.stream_info_mut().set_block_sizes(max, max)?; // spec: min excludes the last block
let mut sink = flacenc::bitsink::ByteSink::new();
stream.write(&mut sink)?;               // sink.as_slice() = the FLAC bytes
// phone: claxon::FlacReader::new(Cursor::new(bytes))?.samples() -> i32 samples
```

  A clip under 16 samples in total would still be rejected; the protocol should never send one (sentences are seconds
  long). Add a unit test for lengths 4096 + 1..15 in `lectrice-link`.

## 4. RAM per engine (RSS, `/proc/self/status`)

| State | RSS |
|---|---|
| Process before load | 21 MB |
| Fast or Small loaded | 272 MB; **~600 MB** after 3 min of synthesis (onnxruntime arenas grow, then stay) |
| Full loaded | 424 MB; **~710 MB** after synthesis |
| Full + Fast loaded | 800 MB; **1,176 MB** after 10 sentences on each (peak) |

- A second engine costs **~0.35 GB at load, ~0.7 GB once used**. Two engines peak at ~1.2 GB.
- **Decision:** the desktop-spec §2.1 rule "≥ 8 GB total RAM" is safe (conservative) and can stay. Better: also require
  **≥ 1.5 GB available** (`MemAvailable` on Linux, `ullAvailPhys` on Windows) when the helper engine would load; else
  `Busy` as the spec says.
- Small finding: 10 load/unload cycles grew RSS by 40–70 MB (fragmentation). With the 5-min idle unload this is slow
  creep; H1 should soak-test repeated helper-engine load/unload.

## 5. mDNS on Linux (`mdns-sd` 0.21.7, Apache-2.0 OR MIT, next to avahi-daemon)

- Shares UDP 5353 with avahi (and kdeconnectd, chrome, adb, all bound there): no error. `avahi-browse -rt _lectrice._tcp`
  saw it at once: `hostname h0-bench-lectrice.local`, the laptop's LAN address, port 47878, `txt = ["pair=0" "id=…" "v=1"]`;
  `avahi-resolve` resolved the host name. Its own browser resolved it too.
- **It advertises on `lo` (127.0.0.1) by default.** Disable `IfKind::LoopbackV4` / `LoopbackV6` explicitly.
- Interfaces here: `lo` (127.0.0.1, ::1) and `wlp2s0` (a 192.168.x.y/24 LAN address, fe80::…/64). No Docker/libvirt here, so the skip
  list is checked by logic only. 0.21.7 has `IfKind::Predicate(IfPredicate::new(|i| …))`, so a prefix list is a one-liner:
  `d.disable_interface(IfKind::Predicate(IfPredicate::new(|i| SKIP.iter().any(|p| i.name.starts_with(p)))))`.
- **Proposed skip list** (name prefix): `lo`, `docker`, `br-`, `virbr`, `veth`, `vnet`, `vmnet`, `vboxnet`, `tailscale`,
  `wg`, `tun`, `tap`, `zt`, `lxc`, `lxd`, `cni`, `flannel`, `podman`, `utun`; Windows: `vEthernet` (WSL / Hyper-V), names
  containing `VirtualBox`, `VMware`, `Tailscale`, `ZeroTier`, `WireGuard` (Windows names UNVERIFIED → H5).
  **Address rule** on top: advertise only RFC 1918 IPv4 (10/8, 172.16/12, 192.168/16); skip 172.17.0.0/16 (Docker
  default), 192.168.122.0/24 (libvirt default), 100.64/10 (CGNAT, Tailscale), 169.254/16. IPv6 off in v1 (disabled in
  the test; the phone dials IPv4).
